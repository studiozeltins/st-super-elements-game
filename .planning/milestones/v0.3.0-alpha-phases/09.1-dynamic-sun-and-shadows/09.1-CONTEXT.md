# Phase 09.1: Dynamic Sun and Shadows - Context

**Gathered:** 2026-07-14
**Status:** Ready for planning
**Mode:** `--auto` (recommended option auto-selected per gray area; log inline below)

<domain>
## Phase Boundary

Client-only. Make the sun DIRECTION (and therefore cast shadows) drift with the
SAME day/night phase/server clock that Phase 9 already drives — dawn shadows fall
one way, dusk the other — on a **readability-capped arc** that never grazes the
horizon, with **per-frame texel-snapped** shadow basis (no shimmer/crawl under the
pixel filter, no FPS regression), plus a **reduce-motion / `?nomovingsun`** path
that pins the sun to a fixed high-noon key = Phase 9's frozen-sun behavior exactly.

This phase DELIBERATELY reverses Phase 9's decision **D-02** (frozen
`sunDirection/sunRight/sunUp`) and relaxes DAYNITE-01's "sun never moves" clause.
D-02 was a considered default protecting combat readability, shadow-map perf, and
pixel-crawl — this phase must **re-earn** each of those guarantees under a moving
sun (capped arc + per-frame texel-snap + reduce-motion fallback), not discard them.

Requirements: SHADOW-01, SHADOW-02, SHADOW-03, SHADOW-04.

**Out of scope (own phases / deferred):**
- Moon-as-separate-caster, star field, sun/moon billboard sprites — not in SHADOW-*;
  the single directional light stays the one shadow caster all cycle (it represents
  moonlight direction at night).
- Any change to the day/night COLOR pipeline (palette, fog, sky-dome, lanterns) —
  Phase 9 owns that; this phase only adds sun POSITION drift + shadow-basis motion.
- Weather / cloud shadows — deferred milestone-wide.
- Ambient-audio time variants (Phase 10), fireflies (Phase 12) — untouched.

</domain>

<decisions>
## Implementation Decisions

### Sun-arc geometry — where computed, arc shape, the cap (SHADOW-01, SHADOW-02)
- **D-01:** The moving sun direction is derived in the **pure twin `dayNightMath.ts`**
  (zero-THREE, vitest-tested) as a function of `phase01` — same input the color
  keyframes already consume. New pure export (e.g. `sunDir(phase01)` returning a
  unit-direction tuple, or azimuth/elevation pair) so downstream `createDayNightCycle`
  does the `THREE.Vector3` write. Keeps sun position provably synced to the color
  cycle (SHADOW-01: never desynced) and unit-testable without a renderer.
  `[auto] Sun-geometry location — Q: "Where is the moving sun direction computed?" → Selected: "Pure dayNightMath twin (mirrors D-08 phase01 + windMath discipline)" (recommended default)`
- **D-02:** **Arc = capped dome.** Azimuth sweeps continuously with phase (dawn = east,
  dusk = west); elevation follows a dome that **never drops below a readability
  floor** — the CAP is a hard contract (SHADOW-02): sun elevation stays high enough
  that shadows cast by telegraphs/enemies/gem-drops inside the gameplay radius stay
  short and high-contrast at EVERY time of day (ATMO-03 preserved under motion).
  Exact floor/peak angles are tuneable discretion; a sensible starting envelope is
  elevation floor ≈ 40° (dawn/dusk) rising to ≈ 75° (midday) — never near-horizon.
  Encode floor/peak as named `as const` constants in `dayNightMath.ts` and pin the
  **floor invariant** in a vitest assertion (loop all phases, assert elevation ≥ floor).
  `[auto] Arc shape/cap — Q: "How is the arc capped for readability?" → Selected: "Capped dome: azimuth sweeps, elevation held above a tested floor (~40°)" (recommended default)`
- **D-03:** The high-noon **frozen key must equal Phase 9's exact `SUN_OFFSET`
  direction** `(30,50,20)` so the SHADOW-04 fallback is byte-identical to shipped
  frozen-sun behavior. The arc envelope is centered on / passes through this key at
  midday. `SUN_OFFSET` magnitude (light distance) is preserved; only direction drifts.

### Shadow-basis lifecycle — module-const → per-frame mutable (SHADOW-01, SHADOW-03)
- **D-04:** Convert the frozen module consts `sunDirection/sunRight/sunUp`
  (`createMondstadtWorld.ts:151-153`) into **world-held mutable scratch vectors
  recomputed each frame** from the current sun direction, BEFORE the texel snap.
  The Gram-Schmidt basis build (`cross(worldUp, sunDir)` → right, `cross(sunDir,
  right)` → up) moves from module load into the per-frame path. Zero new allocation —
  reuse pre-allocated scratch vectors (same zero-alloc ban as today).
  `[auto] Basis lifecycle — Q: "How do the fixed basis consts become dynamic?" → Selected: "World-held mutable scratch, recomputed per-frame in setShadowFocus" (recommended default)`
- **D-05:** **Sun direction flows into the world through one setter.** Day/night
  computes the direction each frame and writes it via a new
  `world.setSunDirection(dir)` (or a `sunDirection` member on `AmbienceHandles`,
  Claude's discretion) BEFORE `setShadowFocus` runs in the same frame. `setShadowFocus`
  then reads the live basis. Ordering in `createGame.frame()`:
  `daynight.update()` (writes sun dir + colors) → `world.setShadowFocus(px,pz)`
  (rebuilds basis from live dir, snaps, repositions light+target). This keeps
  day/night the SOLE writer of ambience/sun state (mirrors Phase 9's AmbienceHandles
  single-writer contract); the world owns the shadow-camera mechanics.
- **D-06:** `sunLight.position` continues to be `focus + SUN_OFFSET`-style, but with
  `SUN_OFFSET` now recomputed as `sunDir * SUN_DISTANCE` each frame (was a frozen
  vector). `sunLight.target` stays the snapped focus. Both `updateMatrixWorld(true)`
  calls stay.

### Texel-snap correctness under a rotating basis (SHADOW-03)
- **D-07:** **Continuous basis recompute + rely on the slow arc.** The 20-min cycle
  makes per-frame angular delta sub-texel, so snapping in the (slowly) rotating light
  space keeps edges stable — verify in the golem-fight playtest, not by assumption.
  Keep today's snap math (`texelSize = span*2/mapSize`; project focus onto right/up;
  round to whole texels) unchanged EXCEPT the basis is now the live one.
  `[auto] Snap strategy — Q: "How to prevent crawl when the snap grid itself rotates?" → Selected: "Continuous recompute; slow arc keeps per-frame rotation sub-texel; playtest-verify" (recommended default)`
- **D-08:** **Escalation ladder if playtest shows crawl** (do NOT pre-build these —
  ship D-07 first, measure): (a) quantize the sun direction to coarse angular steps
  (e.g. snap azimuth/elevation to N° buckets) so the basis only jumps at discrete,
  visually-masked moments; (b) raise `SHADOW_MAP_SIZE` (1024→2048) only if a
  measured FPS budget allows. Both are contingencies, not defaults.

### Reduce-motion / `?nomovingsun` fallback (SHADOW-04)
- **D-09:** **Two independent triggers pin the sun to the high-noon key:** (a) the
  URL bisect flag `?nomovingsun` (existing `?no*` convention,
  `createGame.ts:295-317`); (b) OS `window.matchMedia('(prefers-reduced-motion:
  reduce)').matches`. Either one → sun POSITION frozen at the D-03 high-noon key
  (= exact Phase 9 basis), so shadow edges are dead still.
  `[auto] Reduce-motion triggers — Q: "What pins the sun to high-noon?" → Selected: "Both ?nomovingsun URL flag AND prefers-reduced-motion media query" (recommended default)`
- **D-10:** **`?nomovingsun` freezes ONLY sun position — the COLOR cycle keeps
  drifting.** Frozen position is not "reduced motion" for the palette; a static sun
  with a still-shifting sky is correct and readable. This is distinct from
  `?nodaynight`.

### Flag interaction & precedence
- **D-11:** **`?nodaynight` (existing, D-09 of Phase 9) implies frozen sun too.**
  When the whole palette is pinned to a neutral day key, the sun pins to the matching
  high-noon key — one frozen frame, clean FPS bisection. Precedence: `nodaynight` ⊇
  `nomovingsun` (nodaynight freezes palette+sun; nomovingsun freezes sun only).
- **D-12:** The moving-sun path is **gated on the same `dayNightEnabled`** already
  computed (`createGame.ts:324`). No new enable plumbing beyond the `?nomovingsun`
  read.

### Verification discipline (best-practice mandate from the invocation)
- **D-13:** **Pure-twin-first, test-first.** All sun-arc math lands in
  `dayNightMath.ts` with vitest coverage BEFORE the renderer wiring: pin the
  elevation floor invariant (SHADOW-02), phase→direction continuity across the 0.99→
  0.01 wrap (no direction snap/flip at midnight), and dawn-vs-dusk azimuth asymmetry
  (SHADOW-01). Mirrors the Phase 8/9 `windMath`/`dayNightMath` triad.
- **D-14:** **FPS gate is a hard acceptance criterion, not a nicety.** Run
  `scripts/fps_playtest.py` during a golem-class fight (use
  `debug_grant_loadout`/`debug_spawn_goliaths`, local only) and confirm no regression
  vs the frozen-sun baseline (SHADOW-03). Two-client LAN glance to confirm both
  clients see the same sun angle (SHADOW-01 is server-clock-driven so this should be
  free, but verify).

### Claude's Discretion
- Exact elevation floor/peak angles and azimuth start/sweep range (start from the
  D-02 envelope; playtest-tune).
- Whether the sun-direction API is `world.setSunDirection(dir)` vs a `sunDirection`
  member added to `AmbienceHandles` — either satisfies the single-writer contract.
- Direction representation in the pure twin (unit-vector tuple vs azimuth/elevation
  pair) — pick whichever tests cleanest.
- Whether azimuth wraps a full 360° over the cycle or mirrors back E↔W through night
  — as long as it's continuous across the phase wrap (no midnight flip) and the
  elevation floor holds.
- `SUN_DISTANCE` constant (preserve current `|SUN_OFFSET|` ≈ 61.6 by default).

</decisions>

## Existing Code Insights

### Reusable Assets
- **Frozen basis math already exists** (`createMondstadtWorld.ts:151-153`) — the
  exact `cross(up,dir)`/`cross(dir,right)` Gram-Schmidt to move per-frame; no new
  algorithm, just relocate module-load → frame path.
- **Texel-snap already exists and is correct** (`:670-683`) — reuse verbatim; only
  the basis it reads becomes live.
- **`dayNightMath.ts` / `createDayNightCycle.ts`** — the Phase-9 pure-twin + sibling-
  factory the sun-arc math slots into with zero new architecture.
- **`?nodaynight` neutral-key freeze** in `createDayNightCycle` — the exact template
  for the `?nomovingsun` freeze branch.
- **`serverClock` `phase01`** — the SAME synced clock; sun drift is free-riding on
  it, guaranteeing SHADOW-01 LAN sync with zero new net code.

### Established Patterns
- **Zero per-frame allocation** — recompute basis into pre-allocated scratch vectors;
  never `new THREE.Vector3()` in `setShadowFocus`/`update`.
- **Single writer** — day/night is the sole writer of sun color/intensity (Phase 9)
  and now sun DIRECTION; the world owns shadow-camera mechanics. Don't let two
  systems write the sun.
- **Pure-twin-first, vitest before renderer** (D-13) — arc math is deterministic and
  testable with no THREE import.
- **`?no*` bisect flags** — `?nomovingsun` joins `?nowind`/`?nosmoke`/`?nodaynight`.
- **Playtest-tuned constants** — angles/floors are `as const` in the pure twin,
  tuned against the golem-fight FPS + readability check, not guessed.

### Integration Points
- `createGame.frame()` ordering (D-05): `daynight.update()` writes sun dir →
  `world.setShadowFocus()` rebuilds basis + snaps. One-line-ish wiring; `createGame`
  is ~1,963 LOC and must not grow logic — push math into the twin/factory.
- `AmbienceHandles` (or a sibling `world.setSunDirection`) gains the sun-direction
  write channel; day/night writes through it, world reads it in `setShadowFocus`.

<specifics>
## Specific Ideas

- The load-bearing contract is **"capped arc re-earns D-02's guarantees under
  motion"** — the elevation floor is what keeps combat readable while the sun visibly
  moves. Treat the floor as a tested invariant, not a magic number.
- **SHADOW-04 must be byte-exact:** the high-noon freeze key = the current
  `SUN_OFFSET` direction so the reduce-motion path reproduces shipped frozen-sun
  behavior with no visible diff.
- **Two freeze scopes, don't conflate:** `?nomovingsun` = sun position only (colors
  still drift); `?nodaynight` = everything (colors + sun). nodaynight ⊇ nomovingsun.
