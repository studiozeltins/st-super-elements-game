# Phase 09.1: Code Review Report

**Reviewed:** 2026-07-14
**Depth:** standard
**Files Reviewed:** 6
**Status:** issues_found

## Summary

Phase 09.1 makes the sun DIRECTION drift on a capped arc driven by the day/night
server clock, with a per-frame texel-snapped shadow basis and a
`?nomovingsun`/reduce-motion freeze. I reviewed for correctness, per-frame
allocation/churn (the CLAUDE.md zero-alloc render rule), and no-legacy hygiene.

**No blockers.** The core math and wiring are sound:

- `sunDir` elevation floor is provably respected — `domeT = 0.5 + 0.5*cos(w) ∈ [0,1]`
  maps to `[FLOOR, PEAK]` at every phase; azimuth is a sine swing that is 0 at noon
  and opposite-signed dawn/dusk. Both are C∞ across the wrap seam.
- The noon key genuinely reproduces the normalized Phase 9 `SUN_OFFSET`
  (verified: `asin(50/√3800) = 54.204°`, `atan2(30,20) = 56.310°`), so
  `SUN_ARC.ELEV_PEAK_DEG` / `AZ_NOON_DEG` are correct to their pinned precision and
  the moving-vs-frozen noon discontinuity is sub-1e-4 — not observable.
- The frozen fallback stays byte-exact: `liveSunOffset` is seeded from the LITERAL
  `SUN_OFFSET` (no normalize→remultiply round-trip) and `setSunDirection` is never
  called when `!movingSunEnabled`, so `sunLight.position = focus + SUN_OFFSET` exactly.
- `setShadowFocus` allocates nothing per frame (all `THREE.Vector3` scratch is
  module-scoped and mutated with `copy`/`crossVectors`/`addScaledVector` in place).
  The Gram-Schmidt basis matches the three.js shadow-camera axes up to sign, and
  texel snapping is sign-invariant, so the snap still holds under the live basis.
- The 30Hz shadow throttle in `createPixelRenderer` is UNCHANGED — `needsUpdate`
  is still set only on alternating frames; no forced per-frame refresh.
- Gating (`movingSunEnabled = dayNightEnabled && !nomovingsun && !reduceMotion`),
  single-writer of the sun direction (only `createDayNightCycle` calls
  `setSunDirection`), colors-still-drift-when-frozen, and frame ordering
  (`daynight.update()` writes `liveSunDir` before `setShadowFocus` reads it) are all correct.
- No stale/misleading "frozen sun" comments remain — every reference accurately
  describes the `?nomovingsun`/reduce-motion fallback.

Findings below are two maintainability/discipline WARNINGs and one minor perf INFO.

## Warnings

### WR-01: `buildSunBasis` is a test-only twin of the production basis — the two can silently drift

**File:** `src/game/systems/dayNightMath.ts:296-326` (twin of `src/game/world/createMondstadtWorld.ts:709-711`)
**Issue:** The Gram-Schmidt light-space basis is implemented TWICE by hand: once in
`buildSunBasis` (exported, unit-tested) and once inline in `setShadowFocus`.
Production never calls `buildSunBasis` — `createMondstadtWorld` does not even import
`dayNightMath`. So the shipped basis (`setShadowFocus`) is validated only indirectly,
through a parallel reimplementation. If someone changes the convention in one place
(e.g. flips a cross-product order or the negate) but not the other, the vitest suite
still passes green against the *stale* twin and gives false confidence, while the real
shadows shift. The doc comment even asserts they must be equal ("must equal the shipped
module-const sunRight/sunUp") but nothing enforces that at build time.
**Fix:** Make one the source of truth. Either (a) have `setShadowFocus` consume a
scratch-writing basis helper shared with the test, or (b) add a test that drives the
REAL `setShadowFocus` (e.g. via a headless world / injected light) and asserts
`sunLight.target.position` / `sunLight.position`, so the production path — not a
hand-mirrored copy — is what's pinned. At minimum, add a comment-level invariant test
that fails if the two diverge.

### WR-02: `sunDir(phase)` allocates a fresh object every frame in the render loop, contradicting the "zero alloc" comments

**File:** `src/game/systems/createDayNightCycle.ts:77-80`; `src/game/systems/dayNightMath.ts:274-285`
**Issue:** When `movingSunEnabled`, `apply()` runs `const d = sunDir(phase)` every
frame, and `sunDir` returns a fresh `{ x, y, z }` object literal each call. The comment
at `createDayNightCycle.ts:74` claims this path is "pure math → world scratch, zero
alloc", and the `dayNightMath` header (line 9) claims "no allocations beyond the single
returned palette struct" — both are now inaccurate: there are two per-frame structs
(`samplePalette` + `sunDir`) in the hottest loop. This codebase treats per-frame render
allocation as a first-order rule (144→20fps regression memory), and `apply()` runs at
the world-tick/frame rate. V8 escape analysis likely mitigates the churn, and it is
consistent with the already-accepted `samplePalette` allocation, so this is not a
blocker — but the "zero alloc" claim should not stand unqualified.
**Fix:** Either update the comments to acknowledge the returned structs, or make
`sunDir` write into a caller-provided scratch (out-param) / a module-level reused vec:
```ts
// dayNightMath.ts
const sunDirScratch = { x: 0, y: 0, z: 0 };
export function sunDirInto(phase: number, out = sunDirScratch) { /* ...; return out; */ }
```
and read `d.x/d.y/d.z` straight into `ambience.setSunDirection` — the value is consumed
immediately and never retained, so a shared scratch is safe.

## Info

### IN-01: `setShadowFocus` rebuilds a constant basis every frame when the sun is frozen

**File:** `src/game/world/createMondstadtWorld.ts:709-711`
**Issue:** The basis rebuild (`negate` + two `crossVectors` + two `normalize`) now runs
every frame unconditionally. When `!movingSunEnabled`, `liveSunDir` never changes, so
this recomputes the exact same `sunRight`/`sunUp` the Phase 9 code held as a precomputed
module constant. It allocates nothing, but it is redundant CPU in the frozen /
reduce-motion path (the accessibility path where you'd most want the cheaper cost).
**Fix:** Optional micro-optimization — expose whether the sun is moving (or a
"basis dirty" flag set by `setSunDirection`) and skip the rebuild when the direction is
unchanged, restoring the frozen path to its Phase 9 cost:
```ts
setSunDirection(x, y, z) { liveSunDir.set(x, y, z); liveSunOffset.copy(liveSunDir).multiplyScalar(SUN_DISTANCE); basisDirty = true; }
// in setShadowFocus: if (basisDirty) { rebuild basis; basisDirty = false; }
```
