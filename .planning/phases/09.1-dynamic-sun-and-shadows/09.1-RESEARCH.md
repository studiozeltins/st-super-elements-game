# Phase 09.1: Dynamic Sun and Shadows - Research

**Researched:** 2026-07-14
**Domain:** three.js DirectionalLight shadow-basis animation under a pixel-filter render target (client-only)
**Confidence:** HIGH (all seams read live; sun geometry computed exactly; no external packages)

## Summary

This is a **pure client rendering refactor**: it converts three module-level constants
(`sunDirection/sunRight/sunUp` at `createMondstadtWorld.ts:151-153`) from frozen values
computed once at module load into world-held scratch vectors recomputed each frame from a
moving sun direction, then re-runs the existing texel-snap on that live basis. All the
arc **math** lands in the existing zero-THREE pure twin `dayNightMath.ts` (vitest-tested
before the renderer wiring); the existing single-writer `createDayNightCycle.update()`
computes the direction each frame and pushes it through the world; `setShadowFocus` reads
it. There is **no new package, no server change, no net code** — the sun rides the same
server-clock `phase01` the color cycle already consumes (SHADOW-01 LAN-sync is free).

The single biggest de-risking finding: **the sun shadow depth map is already re-rendered on
a 30 Hz throttle** (`createPixelRenderer.ts:45,99-103` — `renderer.shadowMap.autoUpdate=false`
and `needsUpdate=true` every *other* frame). The moving sun therefore introduces **zero new
shadow-map GPU cost** — it reuses the existing 30 Hz refresh. The only new per-frame CPU is
~3 cross products (Gram-Schmidt basis rebuild) into pre-allocated scratch, which is negligible.
Changing a DirectionalLight's `position`/`target` per frame recomputes only the light's shadow
camera matrix — it does **not** recompile materials (material re-init is triggered by the
lights-state hash: light count/type/shadow-enable, not direction). `setShadowFocus` already
moves the light every frame today with no recompile, proving this.

**Primary recommendation:** Extend `dayNightMath.ts` with a `sunDir(phase01)` pure function
(raised-cosine elevation dome + sine azimuth swing, both passing through the exact SUN_OFFSET
key at noon, both C∞-continuous across the phase wrap). Add a `setSunDirection(x,y,z)` writer
to `AmbienceHandles`; `createDayNightCycle.update()` writes it; `setShadowFocus` rebuilds the
live basis before the existing snap. Gate motion on `movingSunEnabled = dayNightEnabled &&
!?nomovingsun && !prefers-reduced-motion`; when off, write the **literal `SUN_OFFSET`** (not
trig-at-noon) so SHADOW-04 is byte-exact. Keep the 30 Hz shadow throttle unchanged. Verify
crawl/FPS in the golem playtest (`scripts/fps_playtest.py`) — do not pre-build the D-08 ladder.

### Pattern 1: Byte-exact SUN_OFFSET geometry (the SHADOW-04 / SHADOW-02 anchor)

**What:** The existing frozen sun key, computed exactly this session:
```
SUN_OFFSET = (30, 50, 20)
|SUN_OFFSET|            = 61.644140   → SUN_DISTANCE default  [VERIFIED: computed]
normalized direction   = (0.486664, 0.811107, 0.324443)      [VERIFIED: computed]
elevation above horizon = asin(50/61.644) = 54.204°          [VERIFIED: computed]
azimuth = atan2(x, z)   = atan2(30, 20)  = 56.310°           [VERIFIED: computed]
```
`sunDirection` (light travel, toward target) `= -SUN_OFFSET normalized` — matches
`createMondstadtWorld.ts:151` `SUN_OFFSET.clone().negate().normalize()`.

**When to use:** These are the exact values the noon key of the arc must pass through (D-03),
and the literal vector the frozen fallback must copy.

**Critical:** `[CITED: createMondstadtWorld.ts:151-153]` The frozen basis is built from
`SUN_OFFSET`, not from trig. **Float trig at noon phase will NOT reproduce (30,50,20)** —
`cos/sin(54.204°, 56.310°)` gives `(0.4862, 0.8111, 0.3241)` vs the true `(0.486664,...)`.
So the SHADOW-04 frozen path MUST `sunLight.position.copy(SUN_OFFSET)`-equivalent (reuse the
literal `SUN_OFFSET` `THREE.Vector3` and the existing `sunDirection/sunRight/sunUp` values),
NOT feed `phase=0.5` into `sunDir()`. Recommendation: keep a `FROZEN_SUN_DIR` = normalized
`SUN_OFFSET` and branch to it when `!movingSunEnabled`.

### Pattern 2: The capped-dome arc formulation (concrete trig for `sunDir(phase01)`)

**What:** A direction that (a) never drops below a floor, (b) is C∞-continuous across the
0.99→0.01 wrap, (c) gives distinct dawn/dusk azimuth, (d) passes through the exact noon key.

```ts
// dayNightMath.ts — as-const constants (playtest-tuneable; SEE A1 re: PEAK)
export const SUN_ARC = {
  NOON_PHASE: 0.5,          // midday = brightest palette key (KEYFRAMES[3].phase)
  ELEV_PEAK_DEG: 54.204,    // MUST equal SUN_OFFSET elevation (D-03) — NOT 75° (see A1)
  ELEV_FLOOR_DEG: 40,       // readability floor (SHADOW-02); tune 38–44 in playtest
  AZ_NOON_DEG: 56.310,      // MUST equal SUN_OFFSET azimuth atan2(x,z) (D-03)
  AZ_SWING_DEG: 70,         // dawn/dusk azimuth spread; tune 50–90 in playtest
} as const;

// Continuous, periodic, passes through noon key by construction:
export function sunDir(phase: number): { x: number; y: number; z: number } {
  const p = ((phase % 1) + 1) % 1;
  const w = 2 * Math.PI * (p - SUN_ARC.NOON_PHASE);          // radians from noon
  // Elevation: raised cosine. cos(w)∈[-1,1] → term∈[0,1] → elev∈[FLOOR,PEAK]. Peaks at noon,
  // = FLOOR at midnight (p=0). PROVABLY ≥ FLOOR ⇒ SHADOW-02 invariant.
  const domeT = 0.5 + 0.5 * Math.cos(w);
  const elevDeg = SUN_ARC.ELEV_FLOOR_DEG + (SUN_ARC.ELEV_PEAK_DEG - SUN_ARC.ELEV_FLOOR_DEG) * domeT;
  // Azimuth: sine swing. sin(0)=0 at noon → AZ_NOON exactly (D-03). Dawn (p<0.5) and
  // dusk (p>0.5) get opposite-sign offsets ⇒ distinct dawn/dusk direction (SHADOW-01).
  const azDeg = SUN_ARC.AZ_NOON_DEG + SUN_ARC.AZ_SWING_DEG * Math.sin(w);
  const elev = (elevDeg * Math.PI) / 180;
  const az = (azDeg * Math.PI) / 180;
  const cosE = Math.cos(elev);
  // Convention matches atan2(x,z)=azimuth and y=up (so it reproduces SUN_OFFSET at noon):
  return { x: cosE * Math.sin(az), y: Math.sin(elev), z: cosE * Math.cos(az) };
}
```
**Verification at noon (p=0.5):** `w=0` → `domeT=1` → `elev=54.204°`, `az=56.310°` →
returns `(0.4862, 0.8111, 0.3241)` ≈ normalized SUN_OFFSET (within trig rounding). The MOVING
path may differ from SUN_OFFSET by ~4e-4 at noon — that is fine (arc is continuous); the FROZEN
path uses the literal (Pattern 1) for byte-exactness.

**Why raised-cosine + sine (not a linear ramp):** both are periodic and C∞, so the wrap seam
(0.99→0.01) has no derivative discontinuity — no midnight direction flip (D-13 continuity test
passes by construction). A linear azimuth ramp (`AZ_NOON + 360*(p-0.5)`) also wraps continuously
mod 360 and is a valid discretion alternative (D "azimuth full-360 vs mirror"), but the sine
"mirror" keeps the sun in a front-lit hemisphere and lands noon on `AZ_NOON` exactly.

**Direction representation choice (discretion):** return a unit `{x,y,z}` tuple, not an
azimuth/elevation pair — the world only needs the vector, and the floor invariant is still
testable on the tuple (`Math.asin(dir.y) ≥ FLOOR`). Tuple avoids a second conversion in the
consumer. `createDayNightCycle` writes the three numbers into a world scratch (zero alloc).

### Pattern 3: Live basis rebuild in `setShadowFocus` (D-04) — zero alloc

**What:** Move the Gram-Schmidt from module load (`:151-153`) into the frame path.
```ts
// Module scope — pre-allocated scratch (constructed ONCE, mutated forever):
const WORLD_UP = new THREE.Vector3(0, 1, 0);
const liveSunDir = new THREE.Vector3().copy(FROZEN_SUN_DIR);  // written by setSunDirection
const sunRight = new THREE.Vector3();
const sunUp = new THREE.Vector3();
const liveSunOffset = new THREE.Vector3();   // dir * SUN_DISTANCE, replaces frozen SUN_OFFSET
const shadowFocusScratch = new THREE.Vector3();

// setShadowFocus(x, z): FIRST rebuild basis from the live dir, THEN the existing snap.
sunRight.crossVectors(WORLD_UP, liveSunDir).normalize();
sunUp.crossVectors(liveSunDir, sunRight).normalize();
liveSunOffset.copy(liveSunDir).multiplyScalar(-SUN_DISTANCE);  // dir is light-travel; sun is opposite
// ...existing texel snap on sunRight/sunUp unchanged (:672-678)...
sunLight.target.position.copy(shadowFocusScratch);
sunLight.position.copy(shadowFocusScratch).add(liveSunOffset);
```
**Note the sign:** today `sunDirection = -SUN_OFFSET.normalize()` (points from sun toward focus),
and `sunLight.position = focus + SUN_OFFSET` (sun is at `+SUN_OFFSET`). Keep whichever convention
the plan picks internally consistent — if `setSunDirection` receives the *sun-position* direction
(as `sunDir()` returns, matching SUN_OFFSET), then `liveSunDir` for Gram-Schmidt should be its
negation and `liveSunOffset = dir * +SUN_DISTANCE`. Decide the convention once; unit-test that at
noon the rebuilt `sunRight/sunUp` equal the current module-const values.

### Anti-Patterns to Avoid
- **Feeding `phase=0.5` into `sunDir()` for the frozen fallback** — float trig ≠ literal
  (30,50,20). Breaks SHADOW-04 byte-exactness. Use the literal `SUN_OFFSET`.
- **`new THREE.Vector3()` inside `setShadowFocus`/`update()`** — violates the zero-per-frame-alloc
  ban (CLAUDE.md client-perf). Pre-allocate all scratch at module/factory scope.
- **Forcing `renderer.shadowMap.needsUpdate = true` every frame** to "keep up" with the moving
  sun — doubles the biggest GPU cost, a direct FPS regression (SHADOW-03). The 30 Hz throttle is
  enough for a 20-min arc; leave it (D-07). Escalate via D-08 only if playtest shows crawl.
- **Two systems writing the sun** — day/night must remain the sole writer (D-05). Do not let
  `setShadowFocus` also compute direction; it only *reads* the live dir.
- **Reassigning `AmbienceHandles.sunLight` or swapping the Vector3** — mutate in place; consumers
  hold the reference (overlay pass save/restore-by-reference, Pitfall from Phase 9).

## Common Pitfalls

### Pitfall 1: Stale-depth-map vs live-matrix mismatch on non-update frames
**What goes wrong:** With `shadowMap.autoUpdate=false` and `needsUpdate` every *other* frame,
on the ~30 Hz frames where the depth map is NOT regenerated, the light's shadow-camera matrix
has still moved (basis rotated + focus re-snapped). Sampling a stale depth map with a moved
matrix can, in theory, shift projected shadow coords → shimmer.
**Why it happens:** The renderer already tolerates this for the player-following focus
(translation) today; the moving sun adds slow rotation.
**How to avoid / why it's likely fine (quantified):** Per Pattern 4, per-frame basis rotation is
~0.05 texel and per-2-frame (one throttle gap) ~0.1 texel — sub-texel, imperceptible. Verify in
the golem playtest (D-14). If crawl appears, D-08 ladder: quantize direction to angular buckets
so the basis only jumps at discrete visually-masked moments.
**Warning signs:** Shadow edges "buzz"/crawl on static props while standing still at dawn/dusk.

### Pitfall 2: Convention sign error (sun above vs light-travel direction)
**What goes wrong:** `sunDir()` returns the direction toward the *sun* (matches SUN_OFFSET),
but the Gram-Schmidt basis and `sunLight.position` need consistent signs. A flipped sign puts
the sun below the horizon or mirrors shadows.
**How to avoid:** Unit-test that the rebuilt basis at noon equals the current module-const
`sunRight/sunUp` (`:152-153`) and that `sunLight.position` at noon equals `focus + SUN_OFFSET`.

### Pitfall 3: Elevation peak mismatch (the D-02 "75°" trap)
**What goes wrong:** Using the D-02 loose envelope's "peak ≈ 75°" makes the midday arc miss the
SUN_OFFSET direction (54.20°) — SHADOW-04's frozen key would visibly differ from the live midday
sun, and the arc would not "pass through this key at midday" (D-03).
**How to avoid:** Pin `ELEV_PEAK_DEG = 54.204` (the SUN_OFFSET elevation). Floor ≈ 40° gives a
~14° swing — subtle but readability-safe. See Assumption A1.
**Warning signs:** A jump in shadow length/angle the instant `?nomovingsun` is toggled at midday.

### Pitfall 4: Forgetting the shadow depth-map already re-renders (over-engineering FPS)
**What goes wrong:** Assuming the moving sun needs a new per-frame shadow re-render and paying
for it → FPS regression.
**How to avoid:** It doesn't. `createPixelRenderer.ts:99-103` already sets `needsUpdate` at
30 Hz. The moving light matrix is picked up on the next scheduled refresh. Leave the throttle.

**Per-frame rotation math (SHADOW-03 evidence):** Cycle = 1200 s. Max azimuth angular rate
(sine swing, AZ_SWING=70°): `70·(2π/1200) ≈ 0.366 °/s ≈ 0.0061 °/frame` at 60 fps. At the
shadow-frustum edge (span 45 u): `45·sin(0.0061°) ≈ 0.0048 u`. Texel size =
`(45·2)/1024 = 0.0879 u`. → **~0.055 texel/frame** (~0.11 texel across one 30 Hz gap). Well
under 1 texel ⇒ snapping in the slowly-rotating light space stays stable (D-07 confirmed
quantitatively; still playtest-verify per D-14).
